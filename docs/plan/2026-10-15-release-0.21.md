## 1. Fills hold seats (FR-040), wording and rows (FR-041)
A fill has no position, but it holds a seat so it can never be left out. With `open` the number of empty positions and `fills` the number of fills:
- **Reserved** seats are `min(fills, open)`. The count shown is `seated + reserved`, as `Party (x/y)`. Assigning a fill does not change it.
- **Available** positions are `open - fills`. A position can be picked only while `available >= 1` (a fill picking a position for themselves counts as moving, so the check is `open >= fills`). The join menu is shown only while `available >= 1`; otherwise the waitlist menu shows, with every role, because a free position may still be reserved.
- Joining as a fill is always possible (a fill beyond the free positions waits as a standby fill and holds no seat until a position opens).
- Waitlist promotion seats the first waiter in a freed position only while `available >= 1` after the seating.
- `/content list` and the schedule use the same count.
Rows read `n. WeaponIcon Weapon - @Player - DutyIcon Duty` (`Open` for an empty position, `Player's choice` for a role-only slot without a pick). "The Company" becomes "Party"; "Sworn" is removed.

## 2. Prefilled start time (FR-037)
The create form's Start field is filled with the current UTC time plus one hour, to the minute (13:20 UTC becomes `2026-10-15 14:20`). The edit form keeps the current start; Fix and retry keeps what was typed.

## 3. Ping once per player (FR-038)
New table `ping_log (content_id, user_id, pinged_at)`, one row per player pinged. The button sends private messages only to signed-up players and fills who have no row and are not the owner; each row is claimed before sending and released if the message fails. It stays enabled while anyone is left to ping and dims when nobody is. The owner still gets a labelled copy listing who was reached now and who could not be reached. Contents pinged before this release have their current players recorded as pinged (migration 0019 backfills). `content.pinged_at` stays, unused.

## 4. Remove player (FR-042)
A **Remove player** button next to Assign fill. It opens a private panel (like Assign fill) with a menu of everyone on the roster (seated, fills, waitlist; first 25). Choosing a name removes them, seats the waitlist if a position freed, refreshes the roster and posts one line in the thread mentioning only the removed member. Only the creator and admins can use it; the check is repeated on every click.

## 5. Weapon emojis from the T8 icon (FR-039)
`scripts/sync-emoji.ts` builds each emoji from the tier 8 icon, falls back to the stored tier when the render service has no T8 image, and replaces the existing application emoji of the same name. The linked thumbnails (`weaponIconUrl`) use T8 too. The script is run once at release.

## 6. Permission levels (FR-045)
- **Everyone:** `list`, `me`, `weapon`, `help`, `create`, `history` for oneself, and the roster buttons and menus.
- **Host** (the content's creator): `edit`, `lock`, `unlock`, `cancel`, `end`, `reopen`, `attendance`, `duty`, `assign`, Ping, Remove player.
- **Admin** (an admin role, Manage Server or Administrator): everything a host can do on any content, `history` of any member, `setup`, preset save and delete, the schedule and statistics channels.
No host role is added. Discord cannot hide single subcommands, so refusals are explained in the reply. `/content help` lists the three levels.

## 7. Dashboards (FR-043 schedule, FR-044 statistics)
One mechanism, two kinds. Table `dashboard (guild_id, kind, channel_id, message_ids jsonb, digest text, updated_at)`, primary key `(guild_id, kind)`, row-level security on (migration 0020). `/content setup` gains two channel options (`calendar-channel`, `statistics-channel`; text or announcement channels; `clear-calendar` and `clear-statistics` unset them). Admin only.

**Rules.** The bot only edits and deletes messages it posted itself and recorded. A message deleted by hand is posted again at the next refresh. A refresh renders the message, compares it with the stored digest, and edits only when it changed.

**When.** Events that change the schedule (create, edit, cancel, end, reopen) refresh it right after the reply, best effort and never inside the 3-second window's critical path beyond a single awaited call; everything else, including sign-up counts, refreshes with the scheduled job (every few minutes). Statistics refresh from the scheduled job at most every 30 minutes.

**Calendar layout (owner feedback 2026-10-15: "more like a calendar of events, not a scheduler").** One Components V2 container with the accent colour, a heading `Events Calendar` and `Updated <t:…:R>`. Events already running come first under 🔴 Live now. Then one section per day for the next 7 days (`📆 Thu 15 Oct · Today`, `· Tomorrow`, then weekday and date, all in UTC), days without events are left out. An event is two lines: a UTC time column in a code span, a type icon, the bold title and an `Open ↗` link; then, in small text, type and category, `👥 x/y`, a lock mark when locked, and the viewer's own time and the relative time. More than 12 events (or about 3,500 characters) continue in a second message that repeats the day heading as `(cont.)`; when events drop, the extra message is deleted.

**Statistics.** One container: contents created (all time and last 30 days), cancelled and finished, by type, by category, unique participants, total sign-ups, average fill rate, busiest day and hour (UTC), top hosts, and the 10 most joined players. Players are shown as mentions. No no-show board. Players who left a content are not counted (leaving deletes the sign-up); this is stated in the message footer.
