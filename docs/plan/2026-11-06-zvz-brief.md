# Release 0.32.0 brief: ZvZ

Written at the end of the 0.31.1 session so a new session can start 0.32.0 cold. **Nothing is designed yet.** The owner asked to **brainstorm this together** (ask one question at a time, in plain text; the question-picker tool is declined). Run the guardrail check in `docs/process/guardrails.md` first, then use the brainstorming skill. This is architectural: design, ADR, owner approval, then plan, then build.

## The owner's request (new-requirements.md, item 9, verbatim)
> support making 2 parties, or make an option for 40 players only under ZVZ .. as we will need another new category of content (ZVZ), that supports (Faction warfare, outposts, siege, terry def, castle) how could you design this?

Read `new-requirements.md` (untracked, in `bots/`; the owner's file, do not commit it unasked) for the other ten items, all already built in 0.29.0 to 0.31.1.

## What exists now
- `zvz`, `faction-warfare`, `outposts` (label **Outpost**) and `castle` are already **PvP categories** in `src/domain/kinds.ts` (0.29.0). Siege and territory defense do not exist. Types are PvP, PvE and PvX (PvX is the union of both category lists, capped at 25 options, Training left out).
- Event forums (`event_forum`, type `pvp`, `pve` or any) take normal content by type: `pickEventForum` in `src/domain/card.ts`. CTAs are announced in a text channel with a thread each (ADR 0036).
- A roster has at most **20 positions** (ADR 0004, `MAX_SLOTS` in `src/domain/guided.ts`), numbered by role (ADR 0030).
- Modes already built that ZvZ must work with: Fill with preferences (ADR 0035, `src/domain/fillmatch.ts`), selection mode (applications), waitlist per role, CTA, Blank content (no roster), loot vote, attendance, ping, the calendar.

## Limits to design around
- ADR 0004 caps a roster at 20, so ZvZ needs a new decision that **supersedes it** (mark 0004 superseded, link the new one).
- Discord select menus hold **25 options**: the open-positions menu, the Fill panel, Add player, Remove player, the attendance form and the creation card's count menu (1 to 20) all assume at most 25 entries.
- A Components V2 message holds **40 components** and **4000 characters** of text. 40 numbered rows plus headers is close to that.
- The creation card's slot text field (Details) is limited to 1500 characters; the guided Roles steps count up to 20.
- `slot` has a unique `(content_id, position)`; `sortPositions` renumbers by role after every edit.
- Discord rejects a whole command list for one over-long description: `tests/discord/commands-limits.test.ts` now checks this.

## Update 2026-11-10: the party model is designed for CTA
Questions 2 to 5 below are answered for CTA by [the CTA parties design](2026-11-10-cta-pinned-message-and-parties-design.md) and ADR 0044 (accepted): a `party` on slots, one roster message per party, fill and waitlist per party, host panels asking for the party first, and one function (`maxPartiesFor`) that says how many parties a content may have. The party model is built in 0.31.8 (FR-070), and ZvZ reuses it through `maxPartiesFor`. ZvZ should reuse that model and settle only what is left: type or category (question 1), the party labels, the new categories (question 6) and where it is created (question 7). ADR 0004 is superseded in part by 0044.

## Questions to settle with the owner (one at a time)
1. **Type or category?** The owner wrote "another new category". Is ZvZ a **fourth content type** next to PvP, PvE, PvX (its own forum routing, `forum-type` choice, Type menu entry), or a **category** with a bigger cap? What happens to the PvP categories that share its names today (ZvZ, Faction Warfare, Outpost, Castle): move, copy, or keep?
2. **One roster of 40, or two parties of 20?** "2 parties, or an option for 40 only under ZvZ": is it one choice at creation (1 party of up to 20, or 2 parties), or a fixed 40?
3. **If two parties:** a `party` column on `slot`; two sections in the roster; how a player picks a party; Fill, waitlist and selection per party or across both; callers and duties per party; attendance and ping across both; the party count in the calendar and `/content list` (x/40).
4. **Menus over 25:** how do players pick a position in a 40-position roster (party first, then position; or role first)? Same for Add player, Remove player, the Fill panel and the attendance form.
5. **Creating 40 slots:** presets, the guided Roles steps (count menu stops at 20), the typed list (character limit).
6. **The new categories:** Faction warfare, outposts, siege, territory defense, castle: exact labels, icons, colors, and their forum tags.
7. **Where it is created:** through Normal content with the new type, or its own button in the hub?

## Suggested path
1. Guardrail check, then brainstorm with the owner until the questions above are settled.
2. ADR (supersedes 0004), requirement(s) in `PRODUCT.md`, plan for 0.32.0 in `docs/plan/` (update `2026-11-06-releases-0.29-0.32.md`), owner approves in writing.
3. Build in small `feature/*` branches from `develop`, domain logic pure and tested first, tests before code. Likely order: slot cap and party model (migration), render, join and menus, creation, categories and routing, calendar.
4. Release as in `next-session-handoff.md`.

## Release checklist (what worked for 0.29 to 0.31)
`docker compose run --rm node npm test` and `... npx tsc --noEmit` green, then: `release/x.y.z` branch, bump `package.json` and `package-lock.json` (lines 3 and 9), update `PRODUCT.md` current state and the handoff, `scripts/migrate.ts`, merge to `main`, tag `vx.y.z`, push `main develop vx.y.z`, merge back, wait for the Vercel build (project `prj_r1P9R4PUPeiwLXGGoK347RtiBxkp`, check it is READY), `scripts/register-commands.ts` if commands changed, write `changelog/x.y.z.md` (players' language, how-to steps), `scripts/post-changelog.ts x.y.z --dry-run` then without the flag. Never edit a migration after it ran on production (editing one that only ran on the local test database means resetting that database: `docker compose exec -T db psql -U postgres -c "drop schema public cascade; create schema public;"`).
